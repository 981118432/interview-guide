# 扩散语言模型

几乎所有你使用的 LLM 都是自回归（AR）模型：从左到右，每次前向只输出一个 Token。**扩散语言模型**走的是另一条路线，借鉴了图像生成：从完全被掩码的序列开始，在少数几个步骤中对**所有位置并行**地反复去噪。它带来的收益是吞吐量，据报道可达到每秒 1,000 多个 Token，比经过速度优化的 AR 模型高一个数量级。代价是部分质量损失，而成熟度仍处于早期。本章解释它的工作方式、优势场景，以及工程师在 2026 年真正应该如何使用它。

## 工作方式

AR 模型从左到右分解序列：每个 Token 只根据历史信息预测，每次前向生成一个 Token。**掩码扩散模型**则学习从被破坏（被掩码）的版本中重建完整序列，在少数去噪步骤中同时细化所有位置，并使用**双向**注意力（每个位置既能看到过去，也能看到未来）。

典型参考是 **LLaDA**（arXiv:2502.09992）。从便于教学的角度看，其机制如下：
- **正向过程**：从干净文本开始；在噪声等级 `t` 下，以概率 `t` 将每个 Token 替换为 `[MASK]`。当 `t=1` 时，序列完全被掩码。
- **反向过程**：训练一个 Transformer（“掩码预测器”），同时预测每个被掩码位置的原始 Token，优化的是似然的**下界**（而不是 AR 模型使用的精确似然）。
- **采样**：从完全掩码开始，从 `t=1` 去噪到 `0`。在每一步，模型预测所有被掩码的 Token，**解掩码调度**决定提交多少个置信度最高的预测，以及为下一步重新掩码多少个预测。步骤越少，速度越快但质量越低；每一步只提交一个 Token 会接近 AR 质量，却会失去速度优势。

并行解码和双向上下文由此直接产生，也给了扩散模型一个显著技巧：LLaDA 报告称，它在反转任务（把一首诗倒过来完成）上超过 GPT-4o，因为其目标并不受左到右顺序锁定。

最清晰的思维模型不是“AR 对扩散”，而是两者之间的**插值**，这一点由 Block Diffusion（BD3-LMs，arXiv:2503.09573）确立：把序列拆成多个 Block，在 Block 之间使用 AR，在 Block 内部使用扩散。这弥补了纯扩散难以处理的两点：KV Cache 和可变长度输出；而 Block 大小就是调节旋钮（Block 大小为 1 时是 AR，Block 大小等于整个序列时是纯扩散）。2026 年几乎所有快速系统都带有某种 Block 或半 AR 变体。

## 速度优势与权衡

提速只来自一个地方：**每次前向提交的 Token 数量**。AR 每次输出一个，扩散模型在少数几个步骤中提交多个，因此当模型能够一次解掩码多个位置时，墙钟吞吐量会上升。这是延迟和吞吐量方面的胜利，并不天然意味着质量更好。

据报道的吞吐量（所有数字都是供应商或基准声称，条件各不相同）：商业扩散模型在单张数据中心 GPU 上报告了每秒约 700～1,500 个 Token，厂商将其描述为比经过速度优化的 AR 基线快数倍（代码补全最佳场景最高约 10 倍，推理工作负载则更接近 5 倍）。对某个商业模型的独立测量约为每秒 1,100 个 Token。

权衡来自解掩码调度本身：每一步提交更多 Token 会更快，但可能产生局部不连贯的输出；因此实际最佳质量往往来自每步解掩码更少的 Token，而这会降低速度。根据 2026 年的报道，质量差距如下：
- **在代码上，差距很小。**扩散模型在代码补全基准上大致匹配同级 AR 模型；代码是公认的最佳场景。
- **在知识和困难推理上，差距更大**，目前没有扩散模型达到前沿水平。一个公认的理论阻力是，掩码扩散优化的是似然**下界**，而不是精确似然。

## 混合方案：用扩散起草、用 AR 验证

最具生产相关性的工作正在融合这两种范式：

- **把扩散模型作为推测起草器。**扩散模型并行提出一个 Token Block，AR 模型对其进行验证，从而保留 AR 目标分布，类似于[推测解码](03-speculative-decoding.md)。TiDAR（arXiv:2511.08923）报告称，它的每秒 Token 数约为 AR 的 5 倍，同时缩小了质量差距，被定位为在延迟敏感场景中超越标准推测解码。
- **Block/半 AR 适配。**Fast-dLLM v2（arXiv:2509.26328）把现有 AR 模型（Qwen）改造成 Block 扩散模型，使用按 Block 划分的 KV Cache 和感知置信度的并行解码。这是从已有 Checkpoint 中获得可缓存、高速扩散解码的实用配方。
- **扩散推理的 RL。**d1（arXiv:2504.12216）是首个面向掩码扩散 LLM 的 GRPO 风格 RL（diffu-GRPO），把掩码 SFT 与高效 RL 阶段结合起来，并在数学和规划基准上报告了相对于基础扩散模型的稳定提升。

近期最可能的生产路径不是纯扩散，而是这些混合方案：它们恢复 KV Cache 和质量，同时保留大部分速度。

## 扩散模型的优势与 AR 仍然领先的地方

**扩散模型的优势（结构性优势，而不只是炒作）：**
- **低延迟、高吞吐服务**，这是最主要的使用场景，尤其适合往返延迟占主导的任务（交互式编码、自动补全、实时 Agent）。
- **代码**，代码生成更像来回迭代和精炼，而不是严格顺序生成。
- **填空和多区域编辑**，这是掩码目标天然支持的能力：把相关位置掩码，并一次性重新生成所有位置（例如一次在签名、文档字符串、调用点和测试中一致地加入一个参数），而不是编排多次 AR 调用。
- **反转及顺序无关的推理和规划**，双向上下文在这些任务中有帮助。

**2026 年 AR 仍然领先的地方**：长上下文和 Agent/工具调用工作流（一项 2026 年现实检验研究记录了扩散模型在长上下文处理、KV Cache 效率和函数调用上的弱点）；知识与困难推理的前沿质量；以及纯扩散模型难以处理的超长或可变长度生成，Block/半 AR 变体正是用来弥补这些问题。AR 还积累了多年服务栈和 KV Cache 优化经验，扩散模型生态尚未追上。

## 成熟度与当下行动建议

坦率地说：整体仍处于早期阶段，快速发展的开放研究基础上只有很薄的一层真实商业产品。工程师应该这样做：

1. 对于质量关键、长上下文或 Agent 场景，**不要替换你的 AR 前沿模型**。
2. **在延迟和吞吐量占主导、且输出短到中等长度并具有结构时试点扩散模型**，例如代码补全和填空、批量转换、结构化抽取。商业的 OpenAI 兼容扩散 API 是阻力最小的 A/B 测试方式；如果需要自托管，则选择开放权重模型。
3. **关注混合方案**，而不只是纯扩散，因为 Block/半 AR 加上“扩散起草、AR 验证”很可能是生产路径。
4. **使用真实的解码设置在自己的任务上做基准测试。**获得的质量直接取决于解掩码的激进程度，而供应商的每秒 Token 数通常假设了激进设置。
5. **对“推理扩散模型”的营销保持怀疑**，并用自己的推理评测验证。

## 面试问题

### Q：扩散语言模型与自回归模型有什么区别？它的优势在哪里？

**强回答：**

自回归模型从左到右生成，每次前向生成一个 Token，每个 Token 只根据过去条件化。扩散语言模型从完全掩码的序列开始，在少数步骤中并行地反复为所有位置去噪，并使用双向注意力。实际优势是吞吐量：它每次前向提交许多 Token，而不是一个，因此据报道每秒超过 1,000 个 Token，是经过速度优化的 AR 的数倍。双向性还适合填空和编辑，因为可以掩码多个位置并一次性连贯地重新生成，也适合顺序无关的任务。代价是知识和困难推理上的质量差距，部分原因是掩码扩散优化的是似然下界而不是精确似然，同时长上下文和工具使用能力更弱。因此，我会把它用于代码等延迟敏感、短到中等长度的结构化生成，而不会把它当作前沿模型的替代品。

### Q：如果扩散 LLM 更快，为什么还没有所有人都切换？

**强回答：**

因为速度伴随着真实的权衡，而且生态还很年轻。知识和困难推理上的质量差距仍然明显，速度本身也取决于解掩码有多激进：最佳质量来自每步提交更少的 Token，这会抵消很大一部分速度优势。纯扩散模型处理长上下文和可变长度输出的能力也较弱，且没有 AR 已经积累的成熟 KV Cache 与服务优化。更可能的路径不是全面切换，而是采用 Block 或半自回归模型，以及“扩散作为推测起草器”的混合方案，在保留大量吞吐量的同时恢复缓存和质量。2026 年更务实的做法是：在延迟占主导、输出结构化的场景试点扩散模型，其余场景继续使用 AR 前沿模型。
