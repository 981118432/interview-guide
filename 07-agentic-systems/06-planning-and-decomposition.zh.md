# 规划与分解

规划是让 Agent 能够解决多阶段问题而不“游荡”的“System 2”组件。生产 Agent 已经从简单的 Chain-of-Thought 发展到**递归分解**和**树搜索**，由推理原生模型（Claude Opus 4.7、GPT-5.5 扩展思考、DeepSeek-R2）在内部完成重型规划。

## 规划谱系

| 方法 | 策略 | 复杂度 | 最适合 |
|------|------|--------|--------|
| **线性** | 一次一步 | 低 | 简单工具 |
| **分支** | If-Then-Else 逻辑 | 中 | 条件流程 |
| **层级** | 主计划 -> 子计划 | 高 | 软件工程 |
| **基于搜索** | 在内部尝试多条路径 | 最高 | 科学研究 |

## 静态规划与动态规划

### 静态（Plan-and-Solve）

Agent 写出一个 10 步计划并严格遵循。
- **优点**：性能高，易于并行。
- **缺点**：脆弱。如果第 2 步失败，第 3～10 步都没有意义。

### 动态（自适应）

Agent 写出计划，但在每次工具调用后都**重新评估**。
- **最佳实践**：使用**带检查点的规划**。每完成一个主要子目标，就强制 Agent 把进度“提交”到状态存储，以便计划失败时恢复和“回溯”。

## CoT 与 o1 推理

模型的内部“思考”窗口（推理扩展）充当**隐藏规划器**。
- 不使用单独的“规划 LLM”，而是使用推理模型（Claude Opus 4.7、GPT-5.5 扩展思考、DeepSeek-R2）生成“心理草稿”。
- 这个草稿被转换成**任务 DAG（有向无环图）**，由编排器执行。

## 递归任务分解

对于超大任务（例如“构建一个全栈应用”），使用**子 Agent 派生**。
1. **主 Agent**：把“项目”分解为“前端”“后端”和“数据库”。
2. **子 Agent**：各自接收一个“子目标”，并进行自己的分解。
3. **合并**：主 Agent 合并结果。

**关键细节**：每个子 Agent 只接收**最小上下文**（仅包含所需内容），防止 Token 膨胀和幻觉。

---

## 树搜索（MCTS）

对于高风险决策，在 Agent 循环中使用**蒙特卡洛树搜索（MCTS）**。
- Agent“模拟”10 个可能的工具调用。
- **奖励模型**（或单独的 LLM Prompt）为每次模拟评分。
- Agent 沿着奖励最高的路径执行。

## 面试问题

### Q：如何防止任务分解中的“无限递归”？

**强回答：**

我们实现**分解深度限制**（通常为 3 层）和**粒度检查**。在派生子 Agent 前，询问 Supervisor 模型：“这个任务是否足够小，可以由一次工具调用解决？”如果是，就直接执行；如果不是，就继续分解。我们还使用**全局控制器**跟踪 Agent 总数，防止会耗尽 API 预算的递归炸弹（Fork Bomb）。

### Q：为什么“计划修订”通常比“生成计划”更昂贵？

**强回答：**

计划生成是一次“重新开始”。计划修订需要**重新评估上下文**：模型必须理解已经完成的内容、前一步为什么失败，以及如何修复而不撤销之前的成功。这需要高得多的“推理密度”。生产环境中，我们经常为**修订**步骤使用更大模型（例如 Sonnet 3.7 或 o1），而初始计划生成使用更小模型。
