# 错误处理与恢复

Agent 会以非确定性的方式失败。错误处理已经从“Try-Catch 代码块”转向**Agent 自我纠错**和**有状态回滚**，LangGraph、Microsoft Agent Framework 等框架也提供了原生检查点/恢复原语。

## Agent 失败分类

1. **幻觉工具**：调用不存在的工具。
2. **Schema 违规**：向真实工具传递错误参数。
3. **环境错误**：工具存在，但外部 API 宕机。
4. **逻辑停滞**：Agent 反复执行同一个失败动作（ReAct 的死亡循环）。

---

## 自我纠错循环

错误现在被视为**信息 Token**。

- **模式**：工具失败时，错误消息不只是记录日志，还会作为 Prompt 反馈给模型：“动作因错误 X 失败。反思发生这种情况的原因，并提供替代策略。”
- **推理模型**（Claude Opus 4.7 扩展思考、GPT-5.5 推理、DeepSeek-R2）特别擅长这一点，因为它们会在隐藏 Chain-of-Thought 中“内化”错误，从而获得高得多的一次恢复率。

---

## 有状态回滚（检查点）

对于长时间运行的 Agent，第 9 步出错不应该让整个项目崩溃。

- **检查点**：高可靠系统（使用 LangGraph 或类似框架）会在每次工具调用成功后，把“状态快照”保存到数据库。
- **回滚**：如果 Agent 进入逻辑停滞，Supervisor Agent 可以把**共享状态重置**到第 5 步，即最后一个“安全”状态，并强制它选择不同路径。

## “陷入循环”的修复

无限循环是 Agent 系统最大的成本黑洞。

**解决方案**：**基于计数器的干预**。
1. 如果同一个 `(Tool, Args)` 元组在一次会话中出现 3 次，编排器就中断模型。
2. 注入强制的**“转向指令”**：“你已经尝试搜索‘X’三次了。这条路径已经走不通。你必须尝试其他工具，或承认自己卡住了。”

## 优雅降级

如果高推理 Agent（Claude Opus 4.7、GPT-5.5 reasoning）持续失败，则回退到：
- **简化 Agent**：更小的模型和更少、更可靠的工具。
- **仅 RAG 模式**：禁用动作，只基于知识库提供概念性答案。

## 面试问题

### Q：为什么传统“异常处理”（Try/Catch）不足以应对 Agent 系统？

**强回答：**

在传统软件中，异常是一个“停止”命令；在 Agent 系统中，模型才是“驾驶员”。如果系统直接停止，用户任务就失败了。我们使用**错误注入**代替传统异常处理：在平台层捕获异常，把它转换成模型的**合成观察**，让模型能够绕开失败进行推理。Try/Catch 只能修复代码；错误注入允许模型修复**计划**。

### Q：如何处理“静默失败”（工具返回 200 OK，但数据是错的）？

**强回答：**

静默失败最危险。我们实现**输出验证 Agent**。对于关键步骤，不直接接受工具输出，而是把它传给“验证器 Agent”（通常是更小、更快的模型），它唯一的任务是检查：“这个工具输出真的回答了所提供的查询吗？”如果验证器回答“否”，就像遇到硬错误一样触发自我纠错循环。
