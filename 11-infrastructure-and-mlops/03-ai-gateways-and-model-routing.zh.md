# AI 网关与模型路由

采用路由层的理由如今已经是经验事实，而不是设想。根据 Datadog 的《2026 AI 工程现状》，**69% 的公司在生产中运行三个或更多模型**，而**限流/容量错误是最大的生产故障模式**（约 5% 的请求失败，其中约 60% 由容量驱动）。Datadog 的判断是：规模化可靠 AI 的首要障碍如今是运营复杂度，而不是模型智能。

一旦依赖多个模型且流量不再很小，单一供应商就成为单点故障；凌晨 2 点把你叫醒的往往是限流，而不是模型质量。**AI 网关**是标准缓解方案。本章说明网关的作用、路由和回退方式、2026 年工具版图，以及什么时候真正需要网关。

## 什么是 AI 网关

AI 网关（也称 LLM 网关、LLM 代理或 LLM 路由器）是**应用与模型供应商之间的控制平面**，向上暴露统一的（几乎总是兼容 OpenAI 的）API，并集中处理否则会散落到各个服务中的横切关注点。

| 工作 | 作用 |
|-----|--------------|
| 统一 API | 用一个 OpenAI 风格接口覆盖供应商，不再编写逐供应商胶水代码 |
| 模型路由 | 选择为每个请求服务的模型/部署 |
| 回退链 | 可重试失败时，按顺序尝试下一个供应商/模型 |
| 负载均衡 | 在 Key、区域、部署和供应商之间分摊流量 |
| 带退避的重试 | 指数退避加抖动，并遵守 `Retry-After` |
| 限流处理 | 检测 429，让受限部署冷却并重新路由 |
| 虚拟 Key + 预算 | 为每个 Key/团队设置美元预算和硬上限 |
| 支出追踪 | 按 Key/团队/模型归因 Token 和美元支出 |
| 可观测性 | 集中记录谁调用、尝试了什么、为何失败、谁最终成功 |
| 缓存 | 精确匹配和语义缓存，降低成本与延迟 |
| 护栏 / PII | 在流量汇聚点过滤和脱敏 Prompt/响应 |

思维模型是：网关把应用代码中 `N 个供应商 × M 个关注点` 的胶水问题，转化为一个由策略统一执行的控制点。代价是增加一个网络跳数和一个必须高可用的组件，这正是下文的核心张力。

## 路由策略

路由策略形成一条复杂度和开销逐渐增加的阶梯。粗略规模感（仅为供应商/实践者的数量级数据）：基于规则的路由增加不到约 1ms，Embedding/语义路由约 5ms，更重的 ML 分类器或 LLM-as-router 约 50～100ms；典型模型延迟则为 500～2000ms。

| 策略 | 决策依据 | 最适合 | 开销 | 故障模式 |
|----------|-----------|----------|----------|---------------|
| 静态/手动 | 每条路由硬编码模型 | 简单、可预测的负载 | 约 0ms | 脆弱；无法适应宕机或价格变化 |
| 基于任务 | 任务类型映射到模型 | 已知任务分类 | <1ms | 误分类；分类体系会过时 |
| 基于成本 | 满足约束的最便宜模型 | 成本上限、批处理 | <1ms | 质量可能被饿死；最便宜模型可能限流 |
| 基于延迟 | 观察/预期延迟最低 | 实时 UX | 约 1-5ms | 所有流量涌向一个快端点；冷启动偏差 |
| 基于能力 | 所需能力（长上下文、视觉、工具） | 异构需求 | 1-5ms | 为“最佳”模型过度配置 |
| 语义 | 对请求做 Embedding，匹配路由 | 意图分发、难度混合 | 约 5-50ms | Embedding 漂移；尾部含糊；阈值调优 |
| LLM-as-router | 小型 LLM 分类并选择 | Embedding 遗漏的含糊尾部 | 约 50-100ms | 增加一次有自身成本和故障面的 LLM 调用 |
| 级联 | 先用便宜模型，低置信度时升级 | 规模化成本-质量 | 串行 | 升级查询会双重付费；置信度有噪声 |

实践中有两点重要。**语义路由**通过 Embedding 相似度选路由，不调用 LLM；常见生产模式是两阶段混合：大多数高置信请求由语义路由处理，把含糊尾部交给 LLM-as-router。**级联**是成本杠杆最大的方式：RouteLLM（UC Berkeley/LMSYS，ICLR 2025）报告称，只把一部分调用路由到前沿模型，就能达到其约 95% 的质量，同时把成本降低 45%～85%。这个范围应被理解为特定基准的上限，而不是保证；升级率才是实际成本变量，如果级联让大部分流量升级，节省就很少。

路由和回退可以组合：正常路径按成本/质量/延迟路由，异常路径跨供应商回退以保证可靠性。级联本质上是内置可靠性回退的质量驱动路由。

## 回退与可靠性

这一节直接回答 Datadog 数据：限流导致大多数生产故障，而回退机制是解法。

**回退链**在主供应商返回*可重试*失败（429 限流、5xx、超时、找不到模型）时，向下一个供应商/模型重试。只重试 429 和 5xx 类错误；绝不要重试 400 类客户端错误，因为只会浪费配额。

**正确的重试**遵循三条规则：指数退避（每次失败等待更久）、抖动（随机化等待，避免客户端同步重试形成会加重宕机的惊群）以及遵守 `Retry-After`（OpenAI 和 Anthropic 的 429 响应都会返回它；使用 `max(retry_after, computed_backoff)`）。忽略 `Retry-After` 是最常见的退避 Bug。

**熔断器**全局追踪端点健康度，在失败率跨过阈值时打开，从而不再让每个请求持续轰击宕机或受限供应商。配合冷却时间，在自动恢复前把失败部署暂停固定窗口。

**跨 Key、区域和供应商的负载均衡**会放大有效限流余量，这是解决容量失败最直接的结构性办法。

必须记住的警告是：**盲目重试会在故障期间增加负载，从而放大宕机。** 退避、抖动、熔断器和 `Retry-After` 才是区分“修复限流”的网关和“恶化限流”的网关的关键。见[可靠性模式](../13-reliability-and-safety/03-reliability-patterns.md)。

## 2026 年工具版图

把版本和确切功能声明当作时间点快照，并注意下列部分比较数字来自供应商营销。

- **LiteLLM**（开源、自托管代理 + SDK）是事实标准：通过 OpenAI 格式 API 覆盖 100 多个供应商，支持延迟、用量、成本、最少负载等路由策略、有序回退、带美元预算的虚拟 Key 和原生 OpenTelemetry。常见批评是 YAML 配置难以承受企业治理规模。
- **OpenRouter**（托管聚合器）在 200 多个模型上提供最快的广度和零运维，并透传供应商价格（文档规定 BYOK 费用）。代价是额外外部跳数和数据离开自己的边界。
- **Portkey**（托管，也有自托管层）定位为完整控制平面：路由、回退、Token 级可观测性、语义缓存和护栏。
- **Cloudflare AI Gateway**（托管、边缘）在可观测性和带顺序供应商回退的缓存上很强，但路由逻辑和预算执行较轻。
- **Kong AI Gateway**（API 管理平台）把 LLM 路由（包括语义路由）、重试/回退、语义缓存和 PII 清理带入成熟网关；已经运行 Kong 时最合适。
- **Envoy AI Gateway**（开源、CNCF 生态）提供基础设施级的基于优先级的回退、重试和超时，原生面向 Kubernetes。
- **云原生**路由器（AWS Bedrock 智能 Prompt 路由、Google Vertex）与各自云紧密集成；严格的账户限流仍使多供应商层有价值。

**自托管与托管**的核心权衡是：自托管（LiteLLM、Kong、Envoy）让数据留在边界内、给出完整控制且是严格合规所需，但你必须让代理本身高可用，否则它会成为单点故障。托管（OpenRouter、Portkey、Cloudflare）几乎零运维、采用快速，但数据要经过第三方，同时把它们的可用性继承为硬依赖。

## 架构模式

- **所在位置**：应用服务和供应商之间，以水平扩展服务或 Sidecar 形式存在。所有 LLM 流量都经过它，因此继承任何关键路径基础设施的可靠性要求。
- **网络跳数税**：网关增加一次跳数。可以将它与应用部署在同一区域/VPC/集群，把跳数控制到亚毫秒，保持代理精简，并积极缓存让命中直接跳过供应商。相对于模型 500～2000ms 的延迟，这个跳数不大，但在负载下是真实开销。
- **不要让网关成为 SPOF**：这是核心架构风险。让多个无状态副本位于负载均衡器后面，把共享状态外置（Redis 保存限流和用量计数，数据库保存 Key 和支出），并对副本做健康检查。只运行一个实例的集中式网关，只是**移动**了单点故障。
- **多区域**：每个区域部署副本，优先本地路由，并跨区域/跨供应商回退，使区域故障可以切换到别处。
- **缓存与可观测性**：相同 Prompt 使用精确匹配，近似请求使用语义缓存；OpenTelemetry Span 携带用户/Key、尝试过的模型、失败原因、最终胜出的回退、每步延迟和准确成本。这能让限流故障变得可见，而不再神秘。见[可观测性](../14-evaluation-and-observability/02-observability.md)。

## 现在需要网关吗？

**大概不需要**（使用应用内薄抽象）的情况：只有一个供应商、正在做原型，或只有一两个供应商，且简单封装仍然能放在脑中。直接 SDK 调用更简单，运动部件更少。这与[应对框架变动](../09-frameworks-and-tools/12-navigating-framework-churn.md)中的薄层理念相同。

**需要网关**的情况：以下多个条件成立——3 个以上模型或多个供应商（占 69% 的多数）；多个团队共享模型访问，需要虚拟 Key、预算和支出归因；限流错误已经真实影响你；重试/回退/Key 管理逻辑已经散落在代码库中（这说明采用网关已经不早）；或者无法回答“哪个供应商服务了这个请求？”“每个团队花了多少？”而不另做项目。

**自建还是购买**：1～2 个供应商时，应用内薄抽象最好；需要数据驻留或深度控制且平台团队有余力时，自托管开源网关（先考虑 LiteLLM）最好；想获得能力但不拥有基础设施、可以接受外部依赖时，购买托管服务最好。

**推出顺序**：先以 shadow/observe 模式运行，优先迁移非关键负载；加入虚拟 Key 和预算，先获得归因再执行限制；增加针对最严重限流问题的回退链；可靠性稳定后再加入缓存和路由；在网关成为承重组件前先做到高可用。

## 面试问题

### Q：限流错误是生产环境的首要故障。网关如何帮助你，又可能如何让事情更糟？

**强回答：**
网关可以在多个 Key、区域和供应商之间做负载均衡，放大限流余量；也可以在 429 时通过有序回退链切换到备用供应商，避免单个供应商限流变成硬故障。它还让故障可见：集中式轨迹显示尝试了哪个供应商以及失败原因。如果重试很幼稚，它也会让事情更糟：在供应商已经过载的时刻盲目、立即重试，会增加惊群负载并加深故障。解决方案是带抖动的指数退避、遵守供应商 `Retry-After`，以及在全局停止轰击死亡端点的熔断器。网关自身也必须通过外置状态实现高可用，否则只是把单点故障搬家。

### Q：什么时候完整网关是过度设计，你会怎么做？

**强回答：**
单供应商或原型阶段使用网关是过度设计：它为暂时不需要的能力增加网络跳数和高可用负担。我会使用应用内薄抽象，把供应商 SDK 放在自有小接口之后，并配备基础回退链和退避。当跨入多供应商、多个团队需要预算与支出归因，或持续遭遇限流（大约是重试和 Key 管理逻辑开始在服务间复制的时点）时，再采用真正网关。即便如此，也会先以 shadow 模式推出，并在它成为承重组件前完成高可用。
