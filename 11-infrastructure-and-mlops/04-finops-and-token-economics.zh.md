# FinOps 与 Token 经济学

本章讨论规模化运行 LLM 的**经济学与纪律**：如何建模、归因、预算并从结构上降低 AI 支出。这不是推理内部机制的重复；关于量化、批处理、投机解码、KV Cache 等战术杠杆，请见[成本优化实战](../04-inference-optimization/07-cost-optimization-playbook.md)和[推理章节](../04-inference-optimization/01-inference-fundamentals.md)。

Datadog《2026 AI 工程现状》中的关键发现构成全章锚点：**系统 Prompt 约占输入 Token 的 69%，但只有约 28% 的调用使用 Prompt 缓存。** 大多数生产技术栈中最大且最省力的成本杠杆仍未使用。AI 产品是有成本的商品业务，而不是零边际成本 SaaS，因此利润率思维已经成为工程问题。

## 成本模型

价格按每百万 Token 报价，分为输入与输出，**输出成本明显高于输入**，通常是 3～5 倍甚至更多，因为生成是自回归且受计算限制，而输入是并行 Prefill。（当前各模型价格见[定价与成本](../02-model-landscape/03-pricing-and-costs.md)；价格下降很快，所以应建模*结构*而不是几分几厘。）

每个请求都可拆为叠加的支出层。分别建模，才能让成本可预测并可归因：

| 层 | 由什么驱动 | 行为 | 主要杠杆 |
|-------|-----------|---------------|---------------|
| 系统 Prompt/指令 | 固定脚手架、工具定义、Few-shot | 约占输入 Token 的 69%；不缓存时每次都付费 | Prompt 缓存 |
| 检索/上下文 Token | RAG 块、注入文档、长上下文 | 随 k 和块大小增长，可能压倒一切 | RAG 与长上下文；块预算 |
| 对话/记忆 | 聊天历史、Agent 草稿 | 没有摘要时无限增长 | 窗口化、摘要、压缩 |
| 模型层级 | 前沿、中等、小型/自托管 | 层级间相差 10～100 倍 | 合适规模、级联、路由 |
| 输出长度 | 详细程度、格式、max_tokens | 按更高的输出价格计费 | `max_tokens` 上限、简洁输出契约 |
| 推理/思考 Token | 扩展思考模式 | 按输出价格计费，响应中不可见 | 按任务复杂度启用思考 |
| 重试/开销 | 瞬时错误、护栏重跑 | 失败时倍增 | 有上限的重试、熔断器 |
| Agent 多步骤 | 计划-行动-观察循环、子 Agent | 每一步都倍增整套成本 | 步骤上限、单次运行预算 |

**推理模型和 Agent 是成本倍增器，而且因不可见而最危险。** 扩展思考 Token 按输出价格计费，却不出现在响应中，所以“很短”的调用可能比可见输出显示的成本高一个数量级；据报告分析，倍增范围取决于任务，约为 3～15 倍。Agent 每一步都会倍增*整个* Token 栈，因此正确的衡量单位是**每个任务的成本，而不是每次调用的成本**。报告区间是：聊天轮次以美分计，而多步骤 Agent 任务可能从几十美分到数美元。

可用于教学的单请求成本公式：

```
cost = Σ(layer_input_tokens × in_rate) + (output_tokens + reasoning_tokens) × out_rate
cost_per_task = cost_per_request × expected_steps × (1 + retry_rate)
```

缓存会作为可缓存输入比例的折扣应用。

## 缓存：最大的成本杠杆

这是首要杠杆，正因为锚点数据表明：约占输入 Token 69% 的层（系统 Prompt）是静态且非常适合缓存，但只有约 28% 的调用缓存了它。潜在节省和实际使用之间的差距，是最大且最便宜的可用节省。

**供应商前缀缓存**让重复 Prompt 前缀享受大幅折扣。据报告，折扣约从 50%（OpenAI，超过阈值后自动缓存，无写入费），到约 90%（Anthropic，使用显式 `cache_control` 断点，带少量写入溢价，读取几次后即可盈亏平衡），再到约 75%（Google）。教学时要明确：所谓“节省 50%～95%”只适用于**缓存的前缀**，不是整张账单。

真正抓住它需要纪律：
- **Prompt 从静态到动态排序。** 先放系统指令、工具定义和 Few-shot 示例（稳定前缀），最后放用户查询。精确前缀匹配意味着前面任何变化都会使其后整个缓存失效。
- **稳定前缀。** 缓存区域不要放时间戳、请求 ID 或每次调用的 Nonce；锁定工具定义顺序。
- **关注 TTL 经济学。** 有写入溢价时，缓存只有在读取次数达到盈亏平衡后才划算，突发且复用率低的流量可能没有收益。
- **把每次调用的缓存命中率作为一等指标埋点。** Prompt 重写、模型版本升级和重新排序都会悄悄降低命中率。

不同于前缀缓存，**精确匹配和语义缓存**会为重复*查询*缓存完整响应。精确匹配按字面请求建 Key（便宜且没有误报）；语义缓存对查询做 Embedding，为相似命中提供缓存响应（自然语言流量命中率更高，但存在需要防护的错误命中风险）。可以分层：精确匹配 → 语义 → 前缀，并分别衡量各层命中率。这在计费层体现了[KV Cache 与上下文缓存](../04-inference-optimization/02-kv-cache-and-context-caching.md)中描述的同一 KV 复用。

## 批处理与异步经济学

OpenAI 和 Anthropic 都为异步批处理（输入和输出）提供约 **50% 的折扣**，完成期限约为 24 小时。决策规则很简单：**只要没有人或系统在等待 Token，就使用批处理。** 高价值批处理包括评测与回归套件、批量分类和标注、语料规模摘要与文档处理、Prompt 或模型变更后的回填，以及 Prompt 变体 A/B 测试。对产品的整个离线层不使用批处理，就等于把一半资金留在桌上。

第三条路径是**预留/预配置吞吐**（AWS Bedrock Provisioned Throughput、Azure OpenAI PTU）：无论使用率如何，都按小时费率购买预留容量；据报告，持续负载可节省约 15%～70%，但只有高且可预测的利用率才经济。思维模型类似云计算：波动或不确定需求按 Token（包括批处理）付费；利用率稳定且高时转为预留容量。

## FinOps 纪律

FinOps Foundation 的判断是：许多部署中**推理占 GenAI 总支出的 80%～90%**，所以纪律中心是每次请求的推理经济学，而不是训练。运营核心包括：

- **归因。** 为每次调用标注团队、功能、客户/租户、模型、路由和环境。技术手段是在 API 前放 Token 代理或[网关](03-ai-gateways-and-model-routing.md)，识别每次调用来源。没有归因，就无法计算单位经济学或看到哪些用例值得其成本。
- **先 Showback 再 Chargeback。** 先建设可见性仪表盘（按供应商、模型、团队、租户，带每日预测和突发告警），标签可信后再交给计费团队。
- **单位经济学。** 追踪每个用户、对话、已解决工单/案例的成本，以及 AI 成本占收入和毛利的比例。把 AI 产品当成有成本的商品业务来管理。
- **利润现实。** 报告快照显示，AI 产品毛利率约比传统 SaaS 的 80%～90% 低 25～30 个百分点，因为每次请求都有可变 Token 成本。因此**按结果定价**（每个已解决工单、每个已完成任务）正在增加，报告中有按已解决支持工单收取固定价格的案例。要求是：按结果收费前先知道每个结果的成本。
- **工具。** 网关提供实时的每请求控制和支出上限；FinOps 平台（Helicone、Vantage、Finout、Amnic 及云成本工具）提供跨云分摊和 Chargeback。成熟技术栈两者都运行。标准化之前核验工具的当前状态，因为这个类别变化很快。

## 结构性成本决策

这些架构级选择能带来 2～50 倍的成本变化，超出逐次调用调优：

- **合适规模、级联和路由。** 路由到能达到质量门槛的最便宜模型，仅在低置信度时升级。据报告，在约 95% 质量保持下能节省 45%～85%（FrugalGPT 是经典参考），升级率是实际成本变量。见[AI 网关与模型路由](03-ai-gateways-and-model-routing.md)。
- **自托管与 API 盈亏平衡。** 相对于前沿 API，据报告盈亏平衡点在每月数千万到数亿 Token，但要注意隐藏成本：原始 GPU 租赁只有真实成本的 30%～40%，应乘以约 2.5～3 倍，工程人力往往超过基础设施。2026 年对大多数团队来说，计算完整技术栈后托管 API 更便宜；高且可预测、利用率高的流量或数据驻留需求才会让自托管胜出。见[LLM 基础设施](01-llm-infrastructure.md)。
- **RAG 与长上下文。** 每次查询只需支付少量相关块，比塞入超长 Prompt 便宜得多。小型静态文档集适合长上下文；大型或频繁变化的语料、高查询量适合 RAG。见[RAG 基础](../06-retrieval-systems/01-rag-fundamentals.md)。
- **蒸馏。** 在锁定评测上把小模型微调到与前沿模型相差几个准确率百分点，据报告能把每 Token 成本降低 5～40 倍，高流量时几周到几个月回本；它适合窄领域高频任务，不适合开放式长尾工作。见[知识蒸馏](../03-training-and-adaptation/05-knowledge-distillation.md)和[蒸馏案例](../16-case-studies/19-customer-distillation-pipeline.md)。
- **输出与 Prompt 工程。** 简洁输出契约、`max_tokens` 上限、结构化输出，以及模型可靠后删减 Few-shot 示例，据报告能在质量损失很小的情况下减少 20%～40% Token。

## 成本反模式

| 反模式 | 机制 | 修复 |
|--------------|-----------|-----|
| 没有缓存 | 每次都为静态系统 Prompt（约 69% 输入）重复付费 | 稳定前缀 + 供应商前缀缓存 |
| 模型过大 | 用前沿模型处理小模型即可完成的任务 | 合适规模、级联、路由 |
| 输出无上限 | 没有 `max_tokens`，格式冗长 | 上限和简洁输出契约 |
| 默认开启推理 | 简单任务也使用扩展思考 | 按任务复杂度启用思考 |
| 重试风暴 | 瞬时错误触发无上限重试 | 有上限的重试和熔断器 |
| Agent 循环失控 | 计划-行动循环不终止；工具错误被当作“重试” | 在循环内部设置步骤、Token 和重试硬上限 |
| 记忆无上限 | 历史累积而没有摘要 | 窗口化和摘要 |
| 塞入长上下文 | 默认使用巨大上下文做检索 | 大型/变化语料使用 RAG |
| 没有归因 | 共享支出没有标签 | 网关 Token 代理 + 标签 |
| 离线工作实时化 | 用同步 API 做评测、回填、标注 | Batch API |

有报告的真实事故让 Agent 循环这一行变得具体：失控 Agent 曾在一个周末烧掉数万美元，直到有人发现。循环内部的硬上限，而不是事后告警，才是防御手段。

## 面试问题

### Q：流量不变但 LLM 账单环比翻倍，你如何定位和修复？

**强回答：**
首先是归因：如果每次调用没有经由网关或代理按功能、团队、模型和路由打标签，这是第一项修复，因为无法观测就无法调试。有了归因后，我会按 Token 支出层拆解，并寻找常见原因：Prompt 变化导致缓存命中率下降（系统 Prompt 约占输入 Token 的 69%，所以缓存回归影响巨大）；简单任务被开启了扩展思考（按输出价格计费且响应不可见）；Agent 循环步骤数悄悄增加；输出或对话历史无上限；或者出现重试风暴。最高回报的修复几乎总是恢复 Prompt 缓存，然后缩小模型并限制输出。离线工作（评测、回填）也应迁移到约半价的 Batch API，并设置按功能预算和突发告警，让下一次翻倍在第一天就有人收到通知。

### Q：为什么 AI 产品毛利率低于 SaaS，工程师能做什么？

**强回答：**
因为每个请求都带有可变 Token 成本，AI 产品更像有成本的商品业务，而不是零边际成本软件；报告毛利率约比典型 SaaS 低 25～30 个百分点。工程师从两方面下手。结构上：缓存静态 Prompt 前缀，合理选择模型并级联，用 RAG 替代塞长上下文，把高频窄任务蒸馏到小模型，并对离线层做批处理。运营上：埋点单位经济学（每个对话、每个已解决结果的成本），让定价可以转向按结果收费，但前提是知道每个结果的成本。成本杠杆是工程责任，而不只是财务责任。
