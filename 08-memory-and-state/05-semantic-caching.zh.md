# 语义缓存

缓存已经从精确字符串匹配演进为**语义匹配**。语义缓存通过复用“等价”查询的结果，把成本降低 **30%～70%**，并把延迟从秒级降低到毫秒级。

## 精确缓存与语义缓存

| 特性 | 精确缓存（Redis/Memcached） | 语义缓存（RedisVL/Qdrant） |
|---------|-------------------------------|---------------------------------|
| **键** | 哈希后的查询字符串 | 查询 Embedding 向量 |
| **匹配**| 100% 字符串一致 | 余弦相似度 > 阈值 |
| **效率**| 低（小拼写错误就会导致缓存失效） | 高（理解意图） |
| **风险** | 零 | 语义漂移（返回错误答案） |

---

## 语义匹配流水线

1. **Embedding**：把传入查询转换成向量（例如使用 `text-embedding-3-small`）。
2. **搜索**：在缓存中搜索最近邻。
3. **阈值检查**：如果 `distance < 0.05`（非常相似），就返回缓存结果。
4. **LLM 验证**：对于高风险查询，使用小型“验证器模型”（例如 GPT-5.5-mini、Claude Haiku 4.5）检查缓存响应是否确实回答了新查询。
5. **更新**：如果没有命中，就调用 LLM，并把新结果存入向量缓存。

## RedisVL 与 GPTCache

标准技术栈：
- **RedisVL**：直接在 Redis 实例中提供低延迟向量搜索。
- **混合缓存**：同时使用 Redis 存储元数据（键）和向量负载。
- **TTL**：语义缓存应该设置 TTL（生存时间）。常见模式是**动态 TTL**：热门答案保留更长时间，同时定期淘汰“过时”信息。

## 多模态语义缓存

随着原生多模态前沿模型（Gemini 3.1 Pro、GPT-5.5、Claude Opus 4.7）的出现，我们现在也会缓存**图像和音频查询**。
- **视觉相似度**：如果之前处理过语义相似的图像，就缓存该图像的描述。
- **音频指纹**：为相似的语音命令缓存转写结果。

## 面试问题

### Q：缓存中的“语义漂移”是什么，如何防止？

**强回答：**
语义漂移发生在相似度阈值过于宽松时（例如 0.8 而不是 0.95）。查询“如何修理我的汽车？”可能会匹配到“如何清洗我的汽车？”的缓存响应。我们使用**多阶段校验**防止这种情况：1）向量相似度检查；2）**实体匹配检查**（确保两个查询都涉及“汽车”和相同的“动词”）；3）**收紧阈值**：对于技术或医疗查询，要求相似度 **>0.98** 才返回缓存结果。

### Q：为什么低流量时语义缓存有时比直接调用 LLM 更贵？

**强回答：**
因为语义缓存自身需要一次**Embedding API 调用**和一次**向量搜索查询**。如果 Embedding 模型成本为 $0.02、搜索耗时 100ms，而主 LLM 调用只需 $0.05、耗时 500ms，那么相对节省就很小。只有在**高规模**场景下，语义缓存才会产生显著收益：此时缓存命中率足够高，可以抵消“Embedding 税”，并大幅降低总体延迟。
