# 短期上下文管理

短期上下文（L1 记忆）是推理发生的高速接口。做好管理已经不再只是维护“消息列表”，而是要进行**KV Cache 优化**和**动态上下文分配**。

## 上下文生命周期

上下文会经历三个阶段：
1. **接收**：用户查询 + 最近历史 + 系统指令。
2. **处理**：GPU 为新 Token 计算 KV Cache。
3. **淘汰**：达到上限后，移除旧 Token，为新 Token 腾出空间。

---

## KV Cache 分块

现代推理引擎（vLLM、TensorRT-LLM）使用 **PagedAttention**。
- **思路**：不再为上下文分配一块连续的 GPU 内存，而是把内存拆成**块**（页）。
- **效率**：通过减少 **60%～80%** 的内存碎片，在相同硬件上支持显著更大的批次和更长的上下文窗口。

## 前缀缓存

这是任何生产级 LLM 技术栈的**延迟圣杯**。
- **问题**：每当 Agent 调用 LLM 时，都会发送相同的 2,000 Token 系统 Prompt + 50 个工具 Schema。这是在浪费计算。
- **解决方案**：**持久化前缀缓存**。服务器把 Prompt 的“静态”部分（前缀）的 KV Cache 保留在内存中。
- **结果**：只需要为消息的*新增*部分付出计算成本并等待计算完成。

## 滑动窗口与摘要

| 方法 | 机制 | 优点 | 缺点 |
|--------|-----------|-----|-----|
| **滑动窗口** | 原样保留最后 N 个 Token。 | 最近内容保真度高。 | “多莉效应”（忘记开头）。 |
| **摘要** | 把旧轮次压缩成文本。 | 保留“关键事实”。 | 丢失细节和格式。 |
| **混合** | 保留最近 10 轮 + 1 份摘要。 | 兼具两者优点。 | 复杂度略高。 |

## 上下文压缩

当前前沿模型支持**Prompt 加固**。
- **选择性丢弃**：自动剥离之前轮次中不相关的“Thought”块，节省空间。
- **Token 剪枝**：使用更小的模型，把较长的用户消息重写成短 50% 但等价的 Prompt，再发送给“推理”模型。

## 面试问题

### Q：什么是“模型上下文窗口”和“应用上下文窗口”的区别？

**强回答：**
**模型上下文窗口**是由架构定义的硬限制（例如 GPT-4o 为 128K）。**应用上下文窗口**是工程师设置的配置（例如限制为 16K），用于管理**延迟和成本**。在生产环境中，我们很少让每轮调用都使用完整模型窗口，因为上下文越大，注意力开销越高，生成速度越慢。我们会设置一个**缓冲区**，为模型的新响应预留空间。

### Q：“前缀缓存”如何改变系统 Prompt 的设计方式？

**强回答：**
它要求我把**静态内容放在前面**，把**动态内容放在后面**。早期的 LLM 模式常常把用户名或日期放在最顶部，这会破坏前缀缓存。我会把“不可变规则”和“工具 Schema”放在开头，把每轮都会变化的“用户上下文”放在末尾。这样所有用户的前 5,000 Token 都相同，从而最大化推理服务器上的缓存命中率。
